# Authenticated V13 benign-control generation

An approval row records an exact control artifact, verified image, attempt,
profile and review evidence digest. Its `recorded_unverified` status alone does
not authorize generation or certify a policy decision.

## Operator flow through Backroom MCP

1. Record the exact control with `record_v13_benign_approval`, including the
   evidence digest and confirmation `RECORD V13 BENIGN CONTROL`.
2. Each of two different reviewers signs in with their own Google staff account
   and calls `attest_v13_benign_approval` with the same approval ID, their review
   reason and confirmation `ATTEST V13 BENIGN CONTROL`. Repeating one account
   does not produce a second review. Both Google subjects and emails must differ.
3. Read `get_v13_trusted_benign_approval`. It refuses missing provenance or a
   stale exact control image/attempt and otherwise returns digest-only receipts.
4. A third operator, who did not attest this control, calls
   `record_v13_private_generation_group` with the exact target bindings,
   approval ID, profile and confirmation `RECORD V13 GENERATION`. For an existing
   verification replay, use `record_v13_replay_private_group` and confirmation
   `RECORD V13 REPLAY GENERATION`.

The Backroom server derives the principal from the authenticated Google session,
checks current write entitlement and OAuth write scope, and sends the assertion
directly to Platform. Tool input cannot supply the principal. Assertions and
secrets are never returned to an operator or browser. Preview sessions cannot
attest or generate.

Both actual Platform group writes require a fresh `generator_assertion` bound
to the approval ID, evidence digest and `authorize-generation` action. Under the
same transaction and approval lock they check the two authenticated reviews,
lock the verified control image, reject any approving generator by subject or
email, and record the authenticated generator email. Missing, forged, expired
or wrongly bound assertions fail closed. The optional authorization preflight
does not replace these checks. Reviews must precede the database start time.

Group and package registrations remain audit records; no private cases are
generated by these MCP calls, and no hold is cleared automatically.

## Configuration and activation

After the migration, deploy Platform and Backroom from the same monorepo change.
Configure the same server-only `DITTO_V13_BENIGN_ATTESTATION_SECRET` (at least 32
characters) in Platform and as an encrypted Cloudflare Worker secret for
Backroom. Missing configuration disables this operation. Keep the value out of
Worker vars, browser bundles, logs and tool inputs. This secret authenticates
the Backroom issuer; the independent humans are the two Google principals,
not two copies of the secret. Existing approval rows need those authenticated
attestations before a group can be created.
